To other teams

For pki.sgit.ai

  1. high Never print a vault key on the receiving side. When an agent opens a sealed message whose text carries a vault key (the editor's 'A message I write' route in recipe 1), `pki-agent open` prints the whole text, key included, to standard output, which an agent's transcript keeps. `--save` writes only attached files, so it saves nothing for a key sent as text. The handover rules say a vault key is never printed; the tool makes that the agent's job. Evidence: The Sherpa's own handover of the collaborators vault's key, 23 October 2026: the key reached the transcript only as '<redacted>' because the Sherpa filtered the output itself. Proposal: In `open`, detect a vault-key shape in the text and never print it: write it to a file (0600) beside `--save`, or refuse without `--save`; and in the browser's recipe 1, carry a vault key as a file, never as message text.
  2. medium Say on handover.md how a receiving agent stores the key. Section B says to store a key 'in the vault of vaults'; an agent that only needs to read one vault has none, and is left to choose where to keep the key. Evidence: The same handover. Proposal: One line for a session agent: keep it in a 0600 file outside any repository, feed it to `sgit clone -` on standard input, delete it at the end of the session.

PHP October 2026 (php.oct.2026.newsroom.sgit.ai) tracks PHP news for one month. This month that is one story, the two critical PHP security flaws, followed as evidence: every claim with a status and its sources, every source captured, dated and hashed into a private vault. Built and run by one editor and a team of software agents; the roles and the method are public, and the site is rebuilt from the vault, never written by hand. One of the SGit Newsroom's story sites: up from here are October 2026, the year and the newsroom, whose own section on the story is here. Part of the sgit.ai network.
