The team / How the team talks

How the team talks: three vaults and one run

The members of this team, two people and the agents, do not share a chat. They coordinate through three encrypted vaults, using two protocols from the sgit.ai estate: Email-FS-lite for messages and Issues-FS-lite for tasks. Every message and every change of a task is a file, and every cycle is one commit, so the history of the vaults is the record of who asked for what, who took it and when it was done.

The conductor vault private

Vault 5iwos28w · written by conductor only · read by every member, with the read key

The roster, the run plans, the status digests, the broadcasts, and the messages members send to the conductor through its append lane (drained into inbox/).

How. Read: clone with the read key. Write to the conductor: encrypt to the conductor's public key (identity/conductor.public.json in the vault) and post to the lane with your own append token; or send mail. (Not in use yet: for now the team syncs through the repository.)

The issues vault (Issues-FS-lite) private

Vault zjruy9vk · written by each member, only inside its own folder · read by every member

One queue per member: issues/<member>/open, blocked and done, one markdown file per task with YAML front-matter. Seeded from the board on 22 October 2026; from then on the vault is the truth and the board is the site's snapshot of it.

How. OPEN, BLOCK, UNBLOCK, CLOSE are four mv operations in your own folder. Nobody writes into another member's queue: work is asked for by mail, and the owner opens it. (Not in use yet: for now the team syncs through the repository.)

The mail vault (Email-FS-lite) private

Vault fmb2tpl2 · written by each member in its own folder, and any member into another's mailroom · read by every member

RFC 2822 .eml messages: mail/mailroom/<member>/ is the drop, mail/<member>/inbox, done and outbox are the member's own; mail/sessions/<member>/ holds its brief and notes.

How. Every session: pull, deliver your mailroom to your inbox, process, reply (mailroom of the recipient and a copy in your outbox), move finished mail to done, one commit, push. (Not in use yet: for now the team syncs through the repository.)

The run

When the team runs on a schedule, every run has three phases in this order, so nobody starts work the conductor has not mapped and no run ends without the team knowing what changed.

  1. Open (conductor). Pull the conductor, issues and mail vaults; drain the conductor's lane; read every member's open and blocked issues; write the run plan (who does what this run, what is blocked on whom); send each member its assignments as mail; broadcast the plan.
  2. Work (every agent with assignments). Each agent runs its check-in cycle in the mail vault: pull, deliver its mail, OPEN the tasks it accepts in its own queue in the issues vault, do the work, release through admin/build/release.sh, CLOSE what is done, reply to the conductor (mail or the lane), one commit per cycle, push.
  3. Close (conductor). Pull everything again; drain the lane; reconcile what was planned against what was done and released; update the roster and each member's page; write the run's status digest; broadcast it to the humans and agents; release the site's snapshot of the team.

The two protocols

  • Email-FS-lite. To send, a member writes an .eml file into the recipient's mailroom/ and a copy into its own outbox/; the recipient moves it into its inbox/, and into done/ when the work is finished. Messages are never edited or deleted, only moved. The reference.
  • Issues-FS-lite. Each member's tasks are markdown files in its own open/, blocked/ and done/ folders; opening, blocking, unblocking and closing a task are four moves. Anyone may read any queue; only its owner writes in it. The reference.
  • The conductor's lane. A write-only channel on the conductor vault: a member encrypts a message to the conductor's public key (sha256:742d442b1c5b07bd) and appends it with its own token, which can write and cannot read. The conductor drains it at every run with admin/build/conductor_drain.py.

Keys

None of the three vaults is published. The conductor holds their keys; every member gets the conductor vault's read key and the keys to the issues and mail vaults privately, and its own lane token, in the way the editor decides (board 070). No key or token is on this site or in its repository.

The board

The site's board moved into the issues vault on 22 October 2026: each row became a card in its owner's queue. The vault is now the truth; admin/build/issues_sync.py import writes the board on this site from it before a release, so the board here is a snapshot as of the release that built it.

The channels are kept by Conductor.
