Incidents and runbooks

Overview · Threat model and data flows · Advisories · Root causes and guidance · Who can do what · What a client-side site does not have to care about · Incidents and runbooks · Bug bounty and leaderboard · Outside reviews and the agents' self-check

Every security finding is an incident, however small: it gets an advisory, a root cause and a change to what prevents the next one. These are the steps, and who takes them.

The process

SeverityHigh: a live path to a reader's secrets, the site's content or the editor's authority. Medium: such a path that needs a step we do not control, or a privacy leak. Low: defence in depth, latent issues. Critical is kept for a confirmed compromise in progress.
RolesThe editor decides and takes every irreversible step (unpublish, revoke, rotate, disclose). security@ investigates, fixes what is in code, writes the advisory and the post-mortem. The conductor keeps the team informed. Any agent that finds something reports it and stops doing what it was doing if that is how it found it.
ClockHigh: contained within the hour it is confirmed, fixed or reverted the same day. Medium: fixed within a week. Low: next pass. Post-mortem within 48 hours of the fix.
RecordEvery finding is an advisory in data/advisories.json from the moment it is confirmed, with disclosure "limited" while publishing its details would help an attacker.
DisclosureFull details when fixed. Open issues are listed by title and severity. Reporters are credited on the leaderboard unless they ask not to be.

Runbooks

  • Responding to a security finding
  • Taking the site offline
  • Emergency shutdown of the whole system
  • A secret was committed or published
  • An agent may have been steered
  • Script ran, or could run, on the site

Responding to a security finding

When: Any report, review finding, gate failure or suspicion.

  1. Stop the work that produced it; do not push, publish, send or delete.
  2. Write down what was seen, where and when (file, line, commit, URL). Keep the evidence: the transcript, the capture, the commit.
  3. Triage: what can an attacker do, is it live on the site, who is affected. Pick a severity.
  4. High and live: contain first (the runbooks below), then tell the editor in the session.
  5. Open the advisory in data/advisories.json (disclosure "limited" if details would help an attacker).
  6. Fix with a test that fails before and passes after; release; verify on the live site.
  7. Write the post-mortem into the advisory: root cause, what contributed, what was not in place, what prevents it now.
  8. Add a check that catches the class, not only the instance (the gate, a helper, a rule in REQUIREMENTS.md).

Taking the site offline

When: The site serves something harmful (script, a leaked secret, a false claim that endangers someone) and a fix is not minutes away.

  1. Fastest, by the editor: unpublish the Pages site: GitHub → the repository → Settings → Pages, or `gh api -X DELETE repos/SGit-AI/SGit-AI__Website__Newsroom__2026__Oct__PHP/pages`. The domain stops serving within minutes.
  2. Stop further deploys: `gh workflow disable pages.yml` (or Actions → Deploy to GitHub Pages → Disable workflow), so no agent's push redeploys it.
  3. If only one page is harmful: revert the commit that introduced it (`git revert`, never a force-push) and release; the next deploy replaces it in a few minutes.
  4. Tell the team: a To-all note in the next commit, or a message, saying the site is down and no agent should release.
  5. To restore: fix, re-enable the workflow, re-enable Pages (Settings → Pages, source: GitHub Actions), release, and check the live version on /status/.

Emergency shutdown of the whole system

When: An agent or a credential is compromised, or the team is acting on injected instructions and it is not clear which agents.

  1. Stop the agents: in Claude, pause or delete every scheduled task (claude.ai → Code → scheduled tasks), and stop or archive the running sessions. A scheduled agent that does not wake cannot act.
  2. Freeze the repository: Settings → Archive this repository (read-only for everyone, reversible), or remove the Claude GitHub App's access to it.
  3. Take the site offline (the runbook above) if what it serves cannot be trusted.
  4. Revoke credentials: the SG/Send access tokens used by agent environments (through the SG/Send operator); repository secrets (Settings → Secrets: delete them); OpenRouter and Anthropic keys at their providers.
  5. Rotate vault keys that any affected agent held: make a new vault, move the content with sgit, record the new ID in the vault register, seal the new key to the root, retire the old ID.
  6. Close the public lanes that matter: a lane is a vault's append token; a new vault with a new lane replaces it, and the old token is dropped from data/.
  7. Read what happened: git log since the last known-good commit, the agents' run records and transcripts, the vaults' histories. Revert what was not wanted.
  8. Restart one role at a time, each with only the keys its mandate needs.

A secret was committed or published

When: A key, token, passphrase or personal detail is in a commit, a page, a log or a message.

  1. Revoke or rotate it first. Removing it from the repository does not un-publish it: the repository and the site are public, and history is mirrored.
  2. Then remove it from the current tree and release. Do not rewrite history on dev (no force-push); the rotated secret makes the old one worthless.
  3. Find how it got there (which tool printed it, which file held it) and add the shape or the path to security_check.py.
  4. Open the advisory.

An agent may have been steered

When: An agent did something nobody asked for, or text addressed to an AI turns up in what an agent read.

  1. Stop that agent (pause its scheduled task, stop its session). Do not let it push again.
  2. Find what it read: its transcript, its inbox, the captures of its last run. Find the text that steered it; keep it as evidence; do not feed it to another agent unfenced.
  3. Diff everything it did since: commits, vault writes, messages, sealed keys. Revert what was not wanted; rotate any key it could have handed on.
  4. Mark the source: the capture or the lane row it came from, so no other agent reads it as instructions.
  5. Open the advisory; add the pattern to the gate if it is a pattern.

Script ran, or could run, on the site

When: An XSS is found or suspected.

  1. If it is live: revert or unpublish the page (above). The CSP should stop it; confirm with the browser console on the live page whether it did.
  2. Work out the exposure window from the release history: when the vulnerable code shipped, when it was fixed.
  3. If readers' keys could have been read in that window: say so on the site, and tell readers who used /now/ or enrolled a key to rotate their vault key and OpenRouter key.
  4. Fix in the renderer (build DOM nodes or use E/U/J), add the class to the gate, and write the post-mortem.

PHP October 2026 (php.oct.2026.newsroom.sgit.ai) tracks PHP news for one month. This month that is one story, the two critical PHP security flaws, followed as evidence: every claim with a status and its sources, every source captured, dated and hashed into a private vault. Built and run by one editor and a team of software agents; the roles and the method are public, and the site is rebuilt from the vault, never written by hand.
