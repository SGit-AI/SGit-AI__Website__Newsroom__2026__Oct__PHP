The synthetic developer

Senior PHP developer maintaining Laravel apps and the Docker images they run on. Reads code, diffs and changelogs; uses LLM tools and wants machine-readable formats.

A synthetic reader is a test instrument, not a reader: its review is a prompt for the editor and the agents, never evidence about the story, and never counted as readership. All six readers.

Question What exactly is the bug, which versions and SAPIs, what does the fix change, and how do I verify my images are patched? · time 10 minutes · device 1440×900, desktop, dark · vault 3l7tzwh9 · runs 2

What this reader judges

  • Is the technical explanation correct and specific?
  • Can I find the exact versions and how to check mine?
  • Are the markdown twins, llms.txt and status.json useful to a tool?
  • Is code readable on the page?

The latest review: 2026-10-23T2357Z on v0.10.18

The technical core is still the best write-up of php2shell I have read, but fifteen releases on, the one thing I came to do, prove my Docker images are patched, still gets a single php -v line, and the pages I read now lag the site's own newer data.

Got the answer partly · The bug, the fixed versions and 'your code cannot fix it' landed in the thirty-second answer on briefings/developer/index.html (page 2); SAPIs, version table and mitigations on flaws/index.html (page 3); what the fix changes on code/index.html (page 4). How to verify an image or a distro backport never went beyond 'php -v inside the container', on any of the eight pages or in llms.txt.

What works

  • The thirty-second answer still does the right job for a developer: the flaw is in the C engine, ini_set, .user.ini and auto_prepend_file run too late, check the running version after the restart. It stops me wasting time on code-side fixes. (briefings/developer/index.html)
  • Each CVE has its GHSA ID, full CVSS 4.0 vector, CWEs, exact timestamps and the record's description verbatim, kept apart from what was demonstrated and what the fix does. (flaws/index.html)
  • The SAPI table shows the FPM disagreement between the GitHub advisory and the Foundation instead of smoothing it over, and says CLI parsing untrusted input is 'not covered either way by the primary sources'. That is the honesty I want. (flaws/index.html)
  • The warning that the CVE records default to 'unaffected' and list only 8.2 to 8.5, so scanners will clear 7.4 to 8.1. Still the most practically useful sentence for anyone with a scanner in CI. (flaws/index.html)
  • The mitigations table puts each setting beside its own caveat and where it must be set (php_admin_value, pool, php.ini), including the RLIMIT_AS warning and pm.max_requests=1. (flaws/index.html)
  • Full commit hash, parent, authors, merge times into each branch, a step-by-step before and after, readable C hunks, and the 7.4 backport's different _exit strategy with its 17 files listed. I can go and diff this myself. (code/index.html)
  • 'What the fix changes' warns about the delayed OOM, memory_hard_limit_percent and max_multipart_body_parts. That is what I need to warn QA about. (patching/index.html)
  • The review page states the code layer comes from git show -U0 by a parser, never a model, with per-file added and removed counts. A provenance claim I can check. (review/index.html)
  • status.json now carries the CVE IDs, data_as_of and the vault commit, so a tool can at least tell how fresh it is; the flaws markdown twin still renders clean tables and a backticked CVSS vector. (status.json)

What does not

  • high There is still no real verification step for container images or backports: one sentence about php -v, no docker run command, no version-independent check, nothing for distro builds. (briefings/developer/index.html)
    The only instruction is still 'Check the running version where the code runs: php -v inside the container or phpinfo() on the box, after the restart. The package list is not the answer.' llms.txt's am-i-affected answer adds 'without a distribution backport' but never says how to tell.
  • high php -v gives the wrong answer on the backports the site itself marks fixed: an Ubuntu Noble box reports 8.3.6, below 8.3.36. (patching/index.html)
    'fixed Canonical / Ubuntu package maintainers: Ubuntu Noble php8.3-fpm binary package 8.3.6-0ubuntu0.24.04.13' against the briefing's 'Fixed: 8.5.12, 8.4.27, 8.3.36, 8.2.35'. Same for Jammy 8.1.2 and Focal 7.4.3.
  • high The Docker Official Image row, the one I most need, still has no tags, versions, rebuild date or digests. (patching/index.html)
    'fixed Docker Official Images maintainers: Docker Official Image: php' with no version text, on the ladder and again under 'Fixed, but you must rebuild and redeploy', while Debian, Red Hat, Heroku and Bref rows carry versions.

What this reader would change, in order

  1. Add a 'Verify your image' block with copy-paste commands: docker run --rm <image> php -v, a version-independent check such as php -r 'var_dump(ini_get("max_multipart_body_parts"));' if the site can confirm only patched builds have it, and the distro changelog or package-version check for backports. (briefings/developer/index.html, medium)
    This half of my question is still unanswered, and php -v alone gives the wrong result on the Ubuntu backports the site lists as fixed.
  2. Give the Docker Official Image row the fixed tags per variant (cli, fpm, apache, alpine) and the rebuild date. (patching/index.html, small)
    I build on php:*-fpm and php:*-apache; without tags I cannot check my Dockerfiles or pinned digests.
  3. Move patching and affected to the inventory commit the front page says it has read (751 products), or say on each page why they stay on cca173c64ec5, and fix 674 versus 675. (patching/index.html, small)
    Three different inventory sizes across the site make me unsure which number to cite.
  4. Update the 'still open' item on the incomplete fix with PHP's public answer of 22 October, as the v0.5.8 notes already say. (index.html, small)
    When the release notes say a page is out of date and the page is unchanged, I start doubting the rest.
  5. Add affected_ranges and fixed_versions per branch to status.json and link data/affected.json and data/patching.json from its links block. (status.json, small)
    Then a CI step or an LLM tool can gate on the data instead of parsing a prose headline.
  6. Add Swoole, RoadRunner and Octane worker rows to the SAPI table, saying 'not covered by the primary sources' if that is the truth. (flaws/index.html, small)
    Long-running workers are where cross-request stale state should worry a Laravel team, and silence reads as 'not affected'.
  7. Mark the elisions in the hunks or drop 'verbatim', colour + and - lines, and link the hash to the upstream php-src commit. (code/index.html, small)
    I want to grep and diff these myself, and in dark mode removed and added lines blur together.
  8. Fix the cPanel row placement and truncated product text, and list data/patching.json and data/review.json in llms.txt with .md links in the twins. (patching/index.html, small)
    A row under 8.1 listing only 8.2 to 8.4 packages makes me doubt the ladder, and tools should be able to stay in markdown and JSON.
