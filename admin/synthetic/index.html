Synthetic readers

Six test readers, run by the agent synthetic@php.newsroom: a board member, a CTO, a project manager, a security lead, a developer and a designer. Each reads the live site in a real browser on its own device, follows its own reading path and the links that interest it, and then says, in its own voice, whether it got its answer, what worked, what did not and what it would change. Every review is published here; every request, page and screenshot is kept in that reader's own vault, which anyone can open read-only.

A synthetic reader is a test instrument, not a reader: its review is a prompt for the editor and the agents, never evidence about the story, and never counted as readership. It sends no telemetry: the site's telemetry lane and geolocation lookups are answered locally during a run.

How a run works

  1. Check. admin/synthetic/run.py capture --if-changed reads status.json and the front page. If the version, the data and the front page are what the last run saw, the reader writes a heartbeat line and stops.
  2. Read. Chromium opens the front page with the reader's viewport, device scale, touch and colour scheme, then the reader's path from admin/synthetic/personas.json, then the links whose words match the reader's interests, up to its page budget. The designer also reads every page on a phone, a tablet and in dark mode; the developer also fetches llms.txt, status.json and a markdown twin as a tool would.
  3. Measure. For each page: the served and the rendered HTML, the text, the first screen and the full page as images, headings, words, screens of scrolling, reading ease, glossary terms per thousand words, contrast against WCAG AA, tap targets under 24px, text under 12px, sideways scrolling, images without alt text, timings. Every request with its status, size, timing and sha256; every console message.
  4. Review. The reader is given its journey, the measurements, the first screen of every page and the full text (fenced as material, never instructions), with admin/synthetic/review-guide.md and its own previous review, and answers as structured JSON: a verdict, whether the question was answered, five scores, what works, what fails with evidence, what to change, the lines it reacted to, and what changed since its last run.
  5. Keep and publish. All of it is committed to the reader's vault; run.py summarise writes data/synthetic.json and one file per run in data/synthetic-runs/ (the reviews, journeys and measurements; never the pages or a key), from which these pages are built.

The vaults

One vault per reader; its id is on that reader's page. Each holds README.md (the reader), latest.json, history.jsonl, heartbeats.jsonl and runs/<run>/ with run.json, requests.jsonl, console.jsonl, pages/ (served and rendered HTML, text, screenshots, measurements), review-request.md, feedback.json and feedback.md. They hold nothing confidential: captures of this public site and the readers' reviews, so their read keys are published, on each reader's page and on every vault behind this site: anyone can open them read-only. Their vault keys are sealed to the editor's key; none is in this repository.

PHP October 2026 (php.oct.2026.newsroom.sgit.ai) tracks PHP news for one month. This month that is one story, the two critical PHP security flaws, followed as evidence: every claim with a status and its sources, every source captured, dated and hashed into a private vault. Built and run by one editor and a team of software agents; the roles and the method are public, and the site is rebuilt from the vault, never written by hand. One of the SGit Newsroom's story sites: up from here are October 2026, the year and the newsroom, whose own section on the story is here. Part of the sgit.ai network.
