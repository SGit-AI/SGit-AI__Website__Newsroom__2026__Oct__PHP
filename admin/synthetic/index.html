Synthetic readers

Six test readers, run by the agent synthetic@php.newsroom: a board member, a CTO, a project manager, a security lead, a developer and a designer. Each reads the live site in a real browser on its own device, follows its own reading path and the links that interest it, and then says, in its own voice, whether it got its answer, what worked, what did not and what it would change. Every request, page, screenshot and review goes into that reader's own private vault.

A synthetic reader is a test instrument, not a reader. Its review is a prompt for the editor and the agents, never evidence about the story, and never counted as readership. It sends no telemetry: the site's telemetry lane and geolocation lookups are answered locally during a run.

How a run works

  1. Check. admin/synthetic/run.py capture --if-changed reads status.json and the front page. If the version, the data and the front page are what the last run saw, the reader writes a heartbeat line and stops.
  2. Read. Chromium opens the front page with the reader's viewport, device scale, touch and colour scheme, then the reader's path from admin/synthetic/personas.json, then the links whose words match the reader's interests, up to its page budget. The designer also reads every page on a phone, a tablet and in dark mode; the developer also fetches llms.txt, status.json and a markdown twin as a tool would.
  3. Measure. For each page: the served and the rendered HTML, the text, the first screen and the full page as images, headings, words, screens of scrolling, reading ease, glossary terms per thousand words, contrast against WCAG AA, tap targets under 24px, text under 12px, horizontal overflow, images without alt text, timings. Every request with its status, size, timing and sha256; every console message.
  4. Review. The reader is given its journey, the measurements, the first screen of every page and the full text, with admin/synthetic/review-guide.md, and answers as structured JSON: a verdict, whether the question was answered, five scores, what works, what fails with evidence, what to change, the lines it reacted to, and what changed since its last run. The review is written by the Claude API when the run has a key, or by an agent session.
  5. Keep. All of it is committed and pushed to the reader's vault; run.py summarise writes this page's data, data/synthetic.json, with no keys in it.

The vaults

One private vault per reader, ids in the table above. Each holds README.md (the reader), latest.json, history.jsonl, heartbeats.jsonl and runs/<run>/ with run.json, requests.jsonl, console.jsonl, pages/, review-request.md, feedback.json and feedback.md. The vault keys are held by the editor and the agent that runs the readers; none is in this repository.

PHP October 2026 (php.oct.2026.newsroom.sgit.ai) tracks PHP news for one month. This month that is one story, the two critical PHP security flaws, followed as evidence: every claim with a status and its sources, every source captured, dated and hashed into a private vault. Built and run by one editor and a team of software agents; the roles and the method are public, and the site is rebuilt from the vault, never written by hand.
